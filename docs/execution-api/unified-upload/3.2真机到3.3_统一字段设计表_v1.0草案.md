# 3.2 真机执行数据 → 3.3 统一字段设计表

版本：`dobot.execution.v1`（建议版本，待双方冻结）  
日期：2026-10-23  
适用范围：Dobot双臂等真机执行数据上传与接收确认。  
交付对象：3.2真机侧接口开发与联调人员。

## 1. 对接范围

本文仅约定3.2真机侧需要交付的数据、字段含义、缺项说明、上传方式和接收回执。

本期采用“一次真机执行结束后上传一个完整快照”。3.2提供实际提交的执行包、网关事件、原子日志、程序终态及已有反馈。未采集的数据允许缺失并注明原因，不要求新增传感器或提供失败归因结论。

程序执行状态与实际任务效果分别填写：程序成功不代表倒液达标；未测量或未验证的效果填写unknown。3.2不需要填写失败类别、根因、置信度或恢复建议。

### 本文符号

P=submitted_package.json；E=gateway_events.jsonl中的一条事件；J=execution_events.jsonl中的一条日志；F=动作反馈对象；T=执行终态事件payload。`[]`表示数组成员。

必填等级：**M**=上传必填；**C**=条件必填；**O**=选填；**M/null**=键必须存在，但事实未知时允许null。条件必填仅约束相关对象已存在的情况，不要求为填字段补造对象。

本规范是待双方冻结的接口草案，上传端点尚未部署。已有字段以真机样例为依据；新增异常正文/堆栈需用新真机记录验证，不能追补历史已丢失内容。

## 2. 报文总体结构：只保留一套事实主线

```text
schema_version / message_id / producer / created_at
identity                  执行、实验、任务、运行及包身份
execution                 程序终态、起止时间、终止方式
devices[]                 本次执行涉及的设备
task                      任务定义、效果目标、约束及版本
plan                      实际提交的节点与依赖图
events[]                  网关事件，保留完整payload和原文
atomic_logs[]             原子日志，独立序号域
result                    实际任务效果及验证证据
data_availability         缺失、部分覆盖和不适用声明
source_documents          原始提交包；其他原文件可通过附件交付
attachments               本期固定为空数组[]
extensions                来源特有扩展
```

3.2无需另行拼装重复的“最终动作结果表”。动作过程通过events表达，动作反馈保留在events[].payload.feedback；同一事实不要求在多个位置分别维护。

### F. 缺失与覆盖状态：固定分类、允许缺证

`data_availability`以下分类键必须存在，每项结构为`{status, missing_reason, evidence_refs}`。

| 分类键 | 描述 | 当前真机预期 |
|---|---|---|
| task_targets | 实际任务目标与验收判据 | unknown/partial |
| recipe | 真实配方实参与版本 | unknown/partial，不因有recipe_id就available |
| device_configuration | 设备配置、标定和能力 | partial/unknown |
| plan | 原提交计划 | available |
| execution_events | 网关完整事件 | available；可疑缺段则partial |
| atomic_logs | 原子日志覆盖 | available/partial，按实际文件 |
| command_feedback | 命令、ACK和到位反馈 | partial，不等于全程连续反馈 |
| task_effect | 液量/溢洒/抓取等效果证据 | unknown |
| media | 可关联的真实视频/图像 | unknown，来源明确未采才not_collected |
| collection_quality | 采样率、掉帧、时钟同步与完整性 | partial/unknown |

status枚举：available、partial、not_collected、not_applicable、unknown。缺失、部分覆盖或未知时必须有missing_reason；available时可为null。evidence_refs为可解析出处数组，无证据为[]。空数组本身不代表“正常”，未出现异常也不能自动证明没有异常。

引用统一采用**当前不可变报文的RFC6901 JSON Pointer**，例如`/events/29/payload/exception_type`；v1不支持跨报文证据引用。previous_message_id仅用于报文修订关联。本期不使用附件引用；事实引用直接指向正文中的具体字段。引用必须指向实际交付的内容，不能只提供接收端无法访问的本地路径。

## 4. 状态、时间、单位的统一语义

1. `execution.status=succeeded`只说明程序正常完成；`result.task_outcome=unknown`和`physical_success_verified=false`可以同时存在，且正是当前成功样例的合理表达。
2. failed终态可确认执行失败；实际液体是否转移、是否达量、是否溢洒仍需效果证据。停止确认是第三类事实，不与前两者互相替代。
3. 网关sequence只在本次执行网关流有序。原子日志以独立文件行定位，不能套用网关序号；不同时间层可以关联但不自动等时。
4. ISO8601保留时区。当前两例网关记录实际为+08:00，不能再次固定加八小时。无逐采样时间保持未知。
5. 关节deg，TCP位置mm/姿态deg，速度为控制器百分比设定。夹爪为原始控制量，目标0闭合/255打开，不能转成力或mm。
6. 参考路径标注为reference；到位误差是摘要。若后续新增连续观测，必须附采样时间、单位、设备/坐标、来源和采样覆盖，不能从摘要插值得到“实测全程”。
7. 未知保留null或缺省，具体受表中M/null/O约束；不要用空字符串代替身份、false代替未知、0代替未测量。
8. 网关事件引用不存在的设备/节点、同事件ID不同内容属于关联冲突；缺乏某类效果测量属于业务缺证，不能作为协议错误一概拒收。

## 5. 上传与接收回执

### 上传接口

建议：`POST /api/v1/robot-executions`，Content-Type为`application/json`。正式地址、端口、认证方式及请求大小上限由联调配置另行提供。本期发送结束快照，不要求实时事件推送。

### 成功回执

新报文持久化完成返回HTTP 201；相同报文重复发送返回HTTP 200，并返回相同receipt_id。

```json
{
  "receipt_id": "<接收记录ID>",
  "message_id": "<原message_id>",
  "execution_id": "<原execution_id>",
  "stored": true,
  "duplicate": false,
  "content_sha256": "<报文内容哈希>",
  "warnings": []
}
```

| 回执字段 | 类型 | 3.2侧使用方式 |
|---|---|---|
| receipt_id | string | 保存接收记录ID，便于联调和上传状态核对 |
| message_id / execution_id | string | 核对回执是否对应本次上传 |
| stored | boolean | true表示本份报文已持久化接收，可结束本次上传重试 |
| duplicate | boolean | true表示相同内容已接收；仍按上传成功处理 |
| content_sha256 | string | 核对接收内容摘要 |
| warnings | array<object> | 每项code/field/message；可接收的缺项或覆盖提醒，不代表上传失败 |

HTTP 2xx但正文缺少必需回执或身份不匹配时，不应直接标记上传成功；记录响应并按相同报文重试或联系联调。接收确认仅表示数据交付成功。

### 重试与冲突

- 相同producer.system_id+message_id、相同正文：返回原receipt_id，不重复接收。
- 相同身份、不同正文：HTTP 409，不覆盖原报文。需修订时使用新message_id并填写previous_message_id。
- 超时、断连或5xx：有界退避重试，保持message_id、created_at和正文不变。
- 400/422：结构或字段不合法，按错误中的field和message修正后作为新报文发送。
- 404：明确引用不存在；409：身份或内容冲突，先核对再处理。
- 401/403：核对认证和访问配置，不循环重试。
- 上传重试只重传数据，不重新执行机械臂动作。

错误响应约定为`{code, message, field, retryable}`，field可为null；retryable仅表示是否适合重传数据。

报文内容哈希为SHA256(UTF-8 JSON，键排序、无多余空白、保留Unicode、禁止NaN/Infinity)。双方固定使用同一规范序列化实现；v1不隐式转换数值、字符串或空值。
